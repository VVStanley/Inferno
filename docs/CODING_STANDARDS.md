# Стандарты кода Inferno

## Назначение и применение

Обязательные требования для проектирования, написания, изменения и ревью GDScript-кода, сцен и ресурсов. Применяй их к затрагиваемой реализации; изменения в существующем коде ограничивай задачей.

- [GAME_DESIGN.md](GAME_DESIGN.md) определяет игровые правила и инварианты.
- [ARCHITECTURE.md](ARCHITECTURE.md) определяет границы компонентов, зависимости и владение данными.
- Этот документ определяет требования к реализации внутри этих границ.

Формулировки «должен», «нельзя», «используй» и «не делай» обязательны. «Предпочитай» обозначает выбор по умолчанию: обоснованное отступление поясняй в результате работы. При противоречии обязательных требований явно укажи его и согласуй решение; не обходи правило молча.

Примеры ниже показывают форму кода и не вводят новые механики или значения баланса. Стандарты не требуют заранее создавать перечисленные классы, каталоги или подсистемы.

## 1. Читаемость и единый стиль

- Используй английские имена с предметным смыслом: `remaining_cooldown_seconds`, `alive_zombie_count`. Отражай единицы измерения там, где возможна неоднозначность.
- Следуй официальному стилю GDScript: `snake_case` для файлов, методов, переменных и сигналов; `PascalCase` для классов, узлов и именованных enum; `CONSTANT_CASE` для констант и элементов enum.
- Для GDScript используй табуляцию, UTF-8, окончания строк LF, отсутствие хвостовых пробелов и один перевод строки в конце файла. Держи строки кода в пределах 100 символов; исключение допустимо для неделимых ссылок и строковых данных.
- Соблюдай порядок объявления: класс и базовый тип, описание, сигналы, enum, константы, поля, методы. Внутри групп придерживайся порядка официального руководства; не оставляй неиспользуемые шаблонные методы.
- Метод должен решать одну понятную задачу. Разделяй его при смешении обязанностей или трудном для чтения потоке управления. Ограничения на число строк сами по себе не заменяют оценку сложности.
- Комментарии объясняют причины, ограничения и неочевидные алгоритмы. Контракт метода описывает допустимые входные данные, результат и существенные побочные эффекты, если они не ясны из имени и типов. Удаляй устаревшие комментарии и закомментированные версии кода.

## 2. Типы, состояния и классы данных

- Типизируй параметры и результаты методов, включая `-> void`, аргументы собственных сигналов, поля и коллекции с известным типом элементов. Вывод типа через `:=` допустим, когда он однозначен и не превращается в `Variant`.
- `Variant`, нетипизированные коллекции и динамические вызовы допускаются на границах API движка или внешних данных, когда тип заранее неизвестен. Проверяй данные на этой границе и передавай дальше определённый тип. Не используй `has_method()` и строковые вызовы как обычную замену известному контракту класса.
- Закрытые наборы состояний и категорий описывай именованными enum. Не сравнивай игровые статусы со строками или числовыми кодами. Enum принадлежит отвечающему за него типу; общий enum нужен только при реальном совместном использовании.
- Переходы состояний выполняй через методы владельца, в которых проверяются допустимые переходы и связанные действия. Не распределяй запись в одно состояние между независимыми потребителями.
- Независимые логические признаки остаются `bool`. Например, видимость сейчас и факт исследования клетки — разные свойства. Взаимоисключающие состояния не представляй набором несогласованных флагов.
- Связанные данные с устойчивым набором полей передавай через типизированный класс данных: обычно `RefCounted`, а при необходимости хранения и редактирования в инспекторе — `Resource`. Используй встроенные типы Godot, когда они уже выражают нужные данные.
- `Dictionary` подходит для настоящего отображения ключей в значения и сериализации. Не передавай внутренние модели и результаты операций как произвольные наборы строковых ключей. Чтение и запись внешнего формата выполняй на границе, с проверкой обязательных полей и типов.

Пример enum внутри скрипта поведения:

```gdscript
enum State {
	WANDER,
	CHASE,
	ATTACK,
}

var _state: State = State.WANDER


func is_attacking() -> bool:
	return _state == State.ATTACK
```

Пример простого класса данных без узла сцены:

```gdscript
class_name DamageInfo
extends RefCounted

var amount: int


func _init(damage_amount: int) -> void:
	amount = damage_amount
```

Проверку допустимости урона и применение к здоровью выполняет владелец соответствующего игрового правила. Класс данных не должен самостоятельно искать цель или менять UI.

## 3. Настройки, константы и отсутствие хардкода

- Настраиваемый баланс храни в типизированных конфигурациях `Resource`, разделённых по ответственности: оружие, актёр, генерация. Общая конфигурация допустима для действительно общих параметров; один глобальный контейнер всех настроек не создавай.
- Локальные параметры представления и сцены допускается задавать через `@export`. Параметры баланса не дублируй в нескольких скриптах, сценах и ресурсах: у каждого значения должен быть один авторитетный источник. Переопределение конфигурации должно быть явным.
- Фиксированные технические ограничения и значимые числовые литералы оформляй именованными `const` рядом с владельцем правила. Очевидные значения вроде нулевого счётчика, единичного приращения и математических коэффициентов с ясным смыслом допустимы непосредственно в выражении.
- Текущее здоровье, боезапас, состояние AI и таймеры экземпляра отделяй от конфигурации. Общий ресурс настроек считай доступным только для чтения во время игры. Правила разделения данных описаны в [ARCHITECTURE.md](ARCHITECTURE.md#5-владение-данными-и-конфигурациями).
- Ограничения инспектора, например `@export_range`, дополняй проверкой обязательных значений и связей между ними при инициализации. Диапазон в редакторе не заменяет проверку данных, поступивших из кода или файла.
- Для действий ввода используй Input Map, для слоёв столкновений — осмысленные имена в настройках проекта и именованные маски в коде. Не размазывай номера клавиш, слоёв и битовых масок по игровой логике.
- Строки для путей ресурсов, действий ввода, анимаций и групп допустимы на соответствующих границах Godot. Повторяемые идентификаторы объявляй у владельца, при необходимости как `StringName`. Не используй отображаемый текст интерфейса для выбора игрового поведения.
- Значения из согласованного дизайна сверяй с [GAME_DESIGN.md](GAME_DESIGN.md). Временные параметры прототипа помечай как временные у источника настройки и указывай в отчёте; не выдавай их за утверждённый баланс.

## 4. Ответственность, DRY и простота

- Разделяй вычисление правил, изменение состояния и представление в соответствии с архитектурными границами. Геттеры и проверки условий не должны незаметно менять игровое состояние.
- Изменяй защищаемое инвариантами состояние через методы его владельца. Не позволяй потребителям обходить правила прямой записью в поля или изменением переданной коллекции. Явно выбирай между общей ссылкой, копией и доступом только для чтения.
- Одно игровое правило должно иметь одну реализацию. Выноси повторяемое знание и поведение, когда у него действительно одинаковые причины изменения; сходство нескольких строк не обязывает создавать общий класс.
- Предпочитай композицию и небольшие предметные методы. Наследование применяй при устойчивом отношении базового и специализированного типов, с сохранением контракта базового типа.
- Не вводи универсальные менеджеры, фабрики, шины событий, глубокие иерархии и абстракции для гипотетических вариантов. Сначала используй существующие возможности Godot и проекта.

### Расширение типов и поведения

- Применяй принцип открытости для расширения и закрытости для изменений к игровым системам: добавление варианта в рамках существующего контракта должно обходиться локальным определением данных или поведения и подключением в месте сборки. Общие правила и независимые потребители не должны требовать новой ветки для каждого вида объекта.
- Разделяй различия в данных и различия в алгоритме. Здоровье, урон, скорость и другие параметры задавай отдельной конфигурацией варианта. Отличающийся алгоритм размещай в самостоятельной реализации поведения или компоненте с понятным типизированным контрактом.
- Потребители должны зависеть от нужной им возможности, её методов и сигналов. Например, нанесение урона не должно проверять конкретный вид врага, а HUD — перечислять виды оружия для чтения одинакового состояния.
- Не распределяй по проекту `if`/`match` по конкретным видам сущностей. Выбор конфигурации или реализации в месте сборки допустим; `match` по закрытому набору состояний также допустим. Общий enum всех разновидностей не должен становиться диспетчером их поведения.
- Новый вариант не требует копирования общей реализации или обязательного нового класса, если меняются только данные. Собственная сцена или скрипт нужны при реальном отличии состава или поведения. Отдельный экземпляр всегда имеет собственное изменяемое состояние.
- Контракт должен быть небольшим и выражать конкретную ответственность. Не создавай один базовый класс со всеми возможностями всех сущностей и набором пустых методов для неподдерживаемых действий.
- При новом требовании, выходящем за существующий контракт, явно пересмотри затронутые границы. Принцип расширяемости не запрещает исправлять общий алгоритм или обоснованно менять контракт; он не требует заранее реализовывать будущие разновидности.

Способ реализации этих границ в Godot и примеры приведены в [ARCHITECTURE.md](ARCHITECTURE.md#расширяемость-игровых-систем).

## 5. Время, жизненный цикл и работа с Godot

- Физическое движение и столкновения обрабатывай в физическом цикле; визуальное обновление — в подходящем цикле представления. Скорости и длительности выражай в явных единицах и учитывай `delta` согласно контракту API, без повторного применения.
- Используй прямые ссылки на методы и сигналы: `health_changed.connect(handler)`, `health_changed.emit(value)`. Подписка должна иметь понятного владельца и не дублироваться при повторной инициализации.
- Для таймеров, tween и `await` учитывай удаление объекта, окончание уровня и повторный запуск операции. Продолжение не должно применять устаревший результат к новому состоянию. Проверки существования объекта недостаточно, если он жив, но операция уже отменена или заменена.
- Освобождай созданные временные узлы и прекращай ненужные действия в рамках их жизненного цикла. Отписывай обработчики, когда подписчик перестаёт участвовать в событии, даже если ещё существует; не добавляй ручную очистку там, где её уже корректно обеспечивает Godot.
- Не обходи всё дерево сцены, не загружай ресурсы с диска и не выполняй тяжёлые пересчёты каждый кадр без обоснования. Оптимизации, пулы и кэши вводи после выявления конкретной стоимости; для кэша определяй источник и условия обновления.
- Не включай `@tool` ради удобства без необходимости: выполнение в редакторе требует отдельной оценки побочных эффектов и корректности жизненного цикла.

## 6. Ошибки и диагностика

- Проверяй обязательные зависимости и конфигурации до первого использования. Ошибка должна указывать компонент, нарушенное условие и полезный контекст, например seed генерации.
- Различай ожидаемый отказ операции и ошибку реализации. Для ожидаемого отказа используй понятный контракт результата: `bool`, допустимый `null`, `Error` или небольшой типизированный результат с enum, в зависимости от необходимых данных.
- Не подавляй ошибки пустым обработчиком, безусловным `return` или скрытой подстановкой значения по умолчанию. Восстановление допустимо, когда оно определено правилами операции и сохраняет игровые инварианты.
- `assert` используй для ошибок разработчика в отладке. Проверки внешних данных и обязательное поведение release-сборки не должны зависеть от выполнения `assert`; не помещай в него необходимые побочные эффекты. См. [GDScript: Assert keyword](https://docs.godotengine.org/en/stable/tutorials/scripting/gdscript/gdscript_basics.html#assert-keyword).
- Диагностика должна помогать воспроизвести проблему. Не оставляй вывод на каждом кадре, секреты или личные данные в логах.

## 7. Проверки и ревью

- Проверяй наблюдаемое поведение и инварианты затронутой механики, включая границы и повторные события. Автоматические проверки должны обнаруживать нарушение правила, а не повторять реализацию. Для простых визуальных правок достаточно соразмерной проверки в целевой среде.
- В тестах генерации фиксируй seed и конфигурацию; учитывай ограничения воспроизводимости из [ARCHITECTURE.md](ARCHITECTURE.md#7-генерация-и-воспроизводимость).
- Проверку загрузки проекта, игрового поведения на ПК и работы на Android учитывай отдельно. Команды запуска указаны в [README.md](../README.md); успешный импорт не подтверждает корректность механики.
- Не отключай предупреждения, типизацию или проверки ради успешного результата. Точечное подавление допустимо с объяснением причины, когда ограничение инструмента подтверждено.
- При ревью указывай конкретное нарушенное правило или наблюдаемый риск. Личные предпочтения, не закреплённые требованиями, обозначай как необязательные предложения.

Перед завершением реализации или ревью проверь:

1. Поведение соответствует задаче и согласованному игровому дизайну.
2. У состояния есть владелец; зависимости и побочные эффекты понятны.
3. Типы, enum и модели данных исключают произвольные строковые статусы и неявные контракты.
4. Настройки имеют один источник; конфигурация отделена от состояния экземпляра.
5. Нет лишнего дублирования правил и необоснованной сложности; добавление разновидности локализовано и не требует проверок её вида в независимых потребителях.
6. Повторные события, таймеры и перезапуск не оставляют устаревших действий.
7. Выполнены соразмерные проверки, а ограничения проверки явно указаны.
8. Итоговое сравнение файлов не содержит посторонних изменений; связанные документы актуальны.

## Основания и примеры из других проектов

Источники изучены 2026-11-10. Ниже указано, какие практики мы приняли для Inferno. Внешние руководства служат объяснением решений; их рабочие процессы, инструменты и требования не становятся обязательными автоматически. Сверяй API с версией Godot проекта.

- [Godot: GDScript style guide](https://docs.godotengine.org/en/stable/tutorials/scripting/gdscript/gdscript_styleguide.html) и [Static typing](https://docs.godotengine.org/en/stable/tutorials/scripting/gdscript/static_typing.html) — основа оформления и типизированных контрактов. Обязательность типов и правила конфигураций выше — принятый выбор Inferno.
- [Pixelorama: CONTRIBUTING.md](https://github.com/Orama-Interactive/Pixelorama/blob/master/CONTRIBUTING.md#code) — пример действующего Godot-приложения, где явно закреплены стиль GDScript, типизация и чистота изменений сцен. Переносим способ фиксации требований; упомянутые там инструменты не устанавливаем автоматически.
- [Pixelorama: AnimationTag.gd](https://github.com/Orama-Interactive/Pixelorama/blob/master/src/Classes/AnimationTag.gd) — реальный типизированный класс данных на `RefCounted` с конструктором и преобразованием в словарь на границе сериализации. Это пример разделения внутренней модели и формата хранения, а не шаблон архитектуры всей игры.
- [Godot: CONTRIBUTING.md](https://github.com/godotengine/godot/blob/master/CONTRIBUTING.md) — пример короткого входного документа со ссылками на подробные обязательные руководства. Аналогично связываем `AGENTS.md` и профильные документы.
- [Google Engineering Practices: What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html) — основание проверять поведение, сложность, полезность тестов и ясность контрактов; отделять обязательные требования от личных предпочтений и избегать обобщений на будущее.
